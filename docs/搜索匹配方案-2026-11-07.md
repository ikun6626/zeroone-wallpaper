# ZeroOne 搜索匹配方案（2026-11-07）

> 目标：解决「搜『二次元』结果为 0，但首页二次元分类有 400+ 张」这类召回问题。
> 本文只出方案，不含代码改动。所有现状结论均来自当次代码阅读 + 线上接口实测。

---

## 0. 一句话结论

后端搜索只查两个字段：`wallpaper.title` 与 `tags.name`，且是 `LIKE '%kw%'` 模糊包含。
「二次元」既不在标题里，也不是任何壁纸的标签（全库标签只有 4 个主题词 + 9 个颜色词），
它只是 **App 首页 UI 里给合辑 `anime` 取的名字**，数据库里没有任何可检索字段叫「二次元」，
所以必然 0 张。

## 2. 同义词 / 近义词扩展

### 2.1 存储方式：先写死（后端常量），后落表

推荐先把词表写死在后端一个 `search-synonyms.ts` 常量（或 `AppApiService` 私有字段）：

- 词量小（< 100 条），无常驻运营编辑需求；
- 改词只需重启后端，**不需要发 App 版本**（App 只发 `keyword`，扩展全在服务端）；
- 避免提前建表带来的 CRUD/权限/缓存成本。

触发落表（`SearchSynonym`）的条件：运营需要每周自助加词，或需要按词加权/下线。
落表形态建议：

```prisma
model SearchSynonym {
  id        Int      @id @default(autoincrement())
  term      String   @unique @db.VarChar(50)  // 用户输入的主词（规范化后）
  aliases   String   @db.VarChar(300)         // 逗号分隔
  expand    String   @default("") @db.VarChar(300) // 实际用于召回的词（空则用 aliases）
  weight    Int      @default(50)
  enabled   Boolean  @default(true)
  updatedAt DateTime @updatedAt
}
```

格式：`canonical → aliases → 召回目标`。召回目标分三类：`tag`（标签名）、`album`（合辑 slug）、`category`（类目名）、`kw`（追加关键词）。

## 3. 分词与模糊：四种方案的代价与适用面

| 方案 | 实现 | 召回提升 | 代价 | 适用面 | 建议 |
| --- | --- | --- | --- | --- | --- |
| `LIKE '%kw%'`（现状） | 无需改 | — | 全表扫描；1619 行量级可接受（≤ 数十 ms） | 短词、精确子串 | **保留为最底层** |
| 中文 2-gram | 服务端把 query 拆 bigram，对 `title + 空格 + tagNames` 拼串 `contains` OR；单字/停用字 bigram 丢弃 | 中：解决「夜景星空」跨词序、少字漏配 | 约 0.5 人日；误召回上升，需要负向词（颜色词不拆） | 2~4 字查询 | **P1 可做，但当前优先级低于同义词** |
| jieba 分词 | Node 侧引入 `nodejieba`/`@node-rs/jieba`（原生编译），服务端构建与部署复杂度上升 | 高（长句） | 1~2 人日 + 运维风险；需维护词典 | 用户输入长句 | **不做**（当前 query 以 2~4 字为主，收益低） |
| MySQL FULLTEXT(ngram) | `ALTER TABLE wallpaper ADD FULLTEXT INDEX ft_title(title) WITH PARSER ngram`；Prisma 不支持 fulltext，需要 `$queryRaw`；`ngram_token_size=2` 需改 `my.cnf` 并重启 | 高 | 2 人日 + DBA 变更窗口；Prisma 查询层要绕开类型系统 | 数据量 > 10 万或需要 BM25 相关度 | **不做**（1619 行，LIKE 足够） |
| 拼音首字母 | 预计算列 `titlePinyin/titleInitials` + pinyin 库 | 中（`eyc`→二次元） | 1 人日 + 需要批量回填 + 发版维护 | 键盘首字母输入习惯 | **不做**（需求未验证，先看搜索日志） |

结论：**这一版只做「同义词 + 类目/合辑兜底」，2-gram 留作 P1，其余不做。**

## 4. 排序：分层召回 + 固定优先级合并（不引入数值打分）

现状服务端按 `publishedAt desc` 输出，客户端只对已加载 30 条重排，因此只要召回 0 条就无从排序。
推荐改成**多次查询分层合并**，层次即优先级，层内仍按 `publishedAt desc`：

| 层 | 召回条件 | 权重分（如需数值） |
| --- | --- | --- |
| L1 精确命中 | `title` 全等 或 `tag.name` 全等 | 100 |
| L2 同义命中 | 同义词展开后的 `tag.name` 全等 / 合辑名全等 | 80 |
| L3 标题包含 | `title contains kw`（现状） | 60 |
| L4 同义词包含 | 展开词对 `title` / `tag.name` 做 contains | 50 |
| L5 2-gram 命中 | bigram 命中数占 query bigram 的比例 | 20 ~ 40 |
| L6 类目/合辑共现兜底 | 命中类目/合辑下的壁纸（按 `publishedAt desc`） | 10 |
| 同层 tiebreak | `viewCount desc` → `id desc`（稳定分页） | — |

实现建议（两段式，成本最低）：

1. 服务端按层各查一次，每层取前 `pageSize*2`，按 `id` 去重后拼成有序候选池（上限 300 条）；
2. 在内存里按「层号 → 发布时间」排序，再按 `page` 切片返回；
3. 响应新增字段 `matchedBy: 'exact'|'synonym'|'title'|'bigram'|'fallback'`，供前端展示「为你推荐」分组（前端 [SearchPage.ets L247-275](../entry/src/main/ets/pages/SearchPage.ets#L247-L275) 可据此替代现有三段式 sort）。

不推荐在 SQL 里算 `CASE WHEN` 分数：MySQL 无法对 `LIKE` 命中位置打分，SQL 复杂度高且难调参。

## 5. 冷启动：标签未入库时的兜底（保证「二次元」出结果）

按以下顺序执行，命中即停（或命中不足时继续叠加）：

1. **类目名匹配**：`Category.name` 包含 query 或包含任一同义词 → 取该类目壁纸（`categoryId in (...)`）。
   - 「二次元」→ 同义词「动漫插画」→ 类目「动漫插画」→ 408 张。
2. **合辑名匹配**：`Album.name` 包含 query/同义词 → 取 `AlbumWallpaper` 关联壁纸（`slug in (...)`）。
   - 「二次元」→ 合辑 `anime`（名称「🌸 动漫插画」）→ 417 张。
3. **标题 LIKE**：现状条件，仍保留。
4. **同义词 kw 扩展**：用 aliases 逐个 LIKE。
5. **仍为 0**：返回 `fallback` 结果（同类目/最邻近义词），同时 `total` 保持真实命中数、另给 `suggestions`；前端文案改为「暂无『X』相关壁纸 · 为你推荐动漫插画」而不是空白页。

硬约束：
- 兜底结果必须带 `matchedBy: 'fallback'`，前端可加「为你推荐」小标题，避免用户误以为精确命中；
- 不伪造条数、不把不相关类目混进「精确结果」；
- 兜底集合必须有上限（如 60 条），否则「二次元」会返回整个 417 张合辑造成翻页疲劳。
